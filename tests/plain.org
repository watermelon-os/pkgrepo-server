* Требования (ТЗ)

** Модель пакетов

- пакет — это имя; версии — записи-артефакты, принадлежащие пакету
- пакет без версий — фантом, фактически ожидание релизов
- имя — группирующий атрибут; «группа пакетов с именем X» — производная от поиска, не отдельная сущность
- версия появляется только из файла-артефакта
- имя и версия берутся из имени файла: парсинг по шаблону пакетной системы (rpm `имя-версия-релиз`, deb `имя_версия_архитектура`); при невозможности разбора — ошибка (позже можно подключать апи репозитория)
- релиз — часть версии, отдельного поля/фильтра нет
- имя пакета не изменяется после создания — переименование это новый пакет и удаление старого
- схема бд проектируется на этапе реализации
- имя и версия ограничиваются по правилам пакетной системы (непустые, без пробелов и разделителей версии); задаются в парсинге имени файла
- веб-интерфейс: код фронта вырезан, зависимости не удаляются

** Сервер

- каждый запрос (команда) получает id: короткий и уникальный
- id пробрасывается через все слои от инициализации до завершения операции
- логи содержат id запроса
- логи — stdout, структурированные
- api — http, данные в json
- url запуска процесса поддерживает шаблонизатор, id передается через url
- url колбэка также содержит id, в него оркестратор передает отчёт
- если БД недоступна — любой запрос, требующий обращения к БД, возвращает ошибку

** Аутентификация

- доступ по токенам; токены объявляются в конфиге: значение, комментарий (назначение), роль
- токены бессрочные, не истекают
- url колбэков для раннеров содержат токен

** Репозитории

- размещение пакета в репозиториях — это выбор репозиториев, в которых пакет будет размещаться; физически это создание ссылок (как `ln`), а не копирование
  - `ln` создает жесткую ссылку: после этого один inode имеет несколько имен (директорий); понятия «оригинал» и «копия» не существует — ни одна из директорий не является «исходной»
  - отдельного хранилища оригиналов нет; файл пакета физически лежит в репозиториях (в один или несколько)
- репозиторий — лишь свойство пакета; размещение не затрагивает журналы и вычисляемые статусы
- репозитории — директории в файловой системе, уже проинициализированные как репозитории (rpm, deb и т.д.)
- проверка проинициализированности — через репо-адаптер (та же команда/скрипт, что обновляет бд репозитория); запасной вариант — маркеры формата (rpm — repodata/, deb — Packages/Release)
- добавление/перезапись файла сопровождается обновлением бд репозитория специфичной для репозитория командой/скриптом
- хэшсумма относится к индексации в фс (учитывает вес файла и т.д.)

** Процессы и оркестраторы

- процессы задаются в связке с пакетом, то есть по имени пакета, а не по конкретной версии
- запуски процессов могут выполняться параллельно; ответственность за сериализацию/параллелизм — на оркестраторе и раннерах
- параллельные запуски разрешены и для одной версии пакета
- таймауты процессов не предусмотрены
- версия для сборки может быть `any` — специальная метка, означающая отсутствие версии
  - в результате сборки раннер в любом случае должен предоставить конкретную версию
  - версия, равная `any`, невозможна — это ошибка
- как раннер получает версию — вне зоны сервера, ответственность конкретного раннера (например гит-теги с префиксом имени программы)
- пакет может не включать процессы; в таком случае тест и сборка для него невозможны

** Журналы и статусы

- журналы тестирования и сборки — разные сущности, не переиспользуемые модели
  - полиморфная модель в бд потребовала бы jsonb, избегаем
  - разные модели — чтобы не делать преждевременную оптимизацию
- журнал тестирования (и сборки) связан с версией пакета
- журнал хранит все записи
- id записи журнала берется из id инициализирующего запроса и устанавливается из кода, а не генерируется бд/случайным механизмом
- группировка записей журнала по id запроса
- статус верификации и статус сборки — вычисляемые значения по последнему завершенному валидному прогону, не хранимые
  - недействительные записи игнорируются при вычислении, даже если это последняя завершенная (успешная)
  - за изменением журнала следует изменение статуса
  - статус всегда актуален и опирается на результаты процессов
- тестирование и сборки можно помечать недействительными

** Колбэк процессов

- на запуск процесса один колбэк, несколько не предусмотрены
- url колбэка содержит id запроса и токен раннера
- body колбэка — plain text в свободной форме (может быть ссылкой на внешний отчёт), никак не обрабатывается
- структурированный результат передается переменными шаблона url колбэка (например `{result}`)
  - обязательные переменные шаблона — часть контракта и документируются, заполняет их раннер
  - сервер парсит их из url и сохраняет, body сохраняет как есть
- `{result}` — фиксированный набор значений: `ok` / `fail`
- ответ на вызов url запуска процесса сохраняется в запись журнала (может содержать ссылку на созданный процесс или мониторинг)
- колбэк с несуществующим id — игнорируется, предупреждение в лог
- повторный колбэк — не перезаписывает запись, игнорируется

** Конфигурация

- источник конфигурации: конфиг-файл, env, затем cli
- приоритет (низший → высший): конфиг-файл, env, cli
- конфиг-файл указывается через cli или берется из пути по умолчанию
- придерживаться gnu стандартов по конфигурации, fhs и т.д. — во всем проекте
- настройки валидируются на старте, некорректные настройки — ошибка
- настройки нельзя изменить пока запущен сервер

** Атомарность

- применимо к добавлению, обновлению, удалению и размещению в репозиториях
- порядок: сначала фс, и только потом бд
  - запись в фс не выполняется в рамках транзакции бд
    - транзакция бд не может откатить фс, а долгая фс-операция внутри транзакции держит блокировки и мешает другим операциям
    - паттерн: файл пишется во временный файл + атомарный rename, затем короткая транзакция бд
- если шаг с фс удался, а запись в бд не прошла — компенсация: удалить записанное
  - один репозиторий — удалить файл
  - несколько репозиториев — удалить созданные ссылки

* Тесткейсы (BDD)

** Сервер

*** SVR-01. Запрос при недоступной БД

- Когда: поступает запрос, требующий обращения к БД, а БД недоступна
- Тогда: возвращается ошибка

*** SVR-02. id запроса

- Когда: сервер принимает запрос (команду)
- Тогда: запрос получает короткий уникальный id
- Тогда: id передается через все операции от инициализации до завершения
- Тогда: логи содержат id запроса
- Когда: запускается процесс
- Тогда: id передается через шаблонизированный url запуска процесса
- Когда: процесс завершается и вызывает колбэк
- Тогда: url колбэка содержит id, в него передается отчёт процесса

*** SVR-03. Синхронизация с фс
- Когда: сервер периодически сканирует репозитории (или по ручному запросу)
- Тогда: подхватываются пакеты/версии, появившиеся на диске вне API
- Тогда: разбор имени файла выполняется по шаблону из конфига (например `{name}-{version}.rpm`)
- Тогда: неразбираемое имя файла только логируется, ошибкой не становится
- Тогда: повторный скан идемпотентен — дубликатов не появляется

** Работа с пакетами

*** PKG-01. Несуществующий пакет

- Когда: происходит обращение к несуществующему пакету
- Тогда: ошибка

*** Добавление пакета

- ADD-01. Добавление с файлом — пакет сразу с первой версией
  - Дано: пакета с таким именем еще нет
  - Когда: выполняется добавление с файлом
  - Тогда: создается пакет сразу с первой версией (минуя фантом)
  - Тогда: файл записывается в фс и бд репозитория обновляется специфичной командой/скриптом
  - Тогда: в бд появляется запись версии

- ADD-02. Добавление без файла — фантом
  - Дано: пакета с таким именем еще нет
  - Когда: выполняется добавление без файла
  - Тогда: создается пакет-фантом: запись пакета есть, файла нет, версий нет

- ADD-03. Дубль версии
  - Дано: версия с таким именем и версией уже существует
  - Когда: выполняется добавление
  - Тогда: ошибка

- ADD-04. Фантом при существующем пакете
  - Дано: пакет с таким именем уже существует (фантом или с версиями)
  - Когда: выполняется добавление без файла
  - Тогда: ошибка — фантом создается только когда пакета еще нет

- ADD-05. url процессов при добавлении/обновлении
  - Когда: добавление/обновление пакета сопровождается установкой url для запуска процессов пакета
  - Тогда: url сохраняется у пакета

*** Обновление пакета

- UPD-01. Перезапись при разной хэшсумме
  - Дано: существует пакет-версия
  - Когда: выполняется обновление с файлом, параметры совпадают, но отличается хэшсумма
  - Тогда: файл в фс перезаписывается, бд репозитория обновляется (как при добавлении)
  - Тогда: хэшсумма пересчитывается
  - Тогда: возвращается варнинг

- UPD-02. Обновление без файла — только поля
  - Дано: существует пакет/версия
  - Когда: выполняется обновление без файла (url процессов, метаданные, имя и т.д.)
  - Тогда: обновляются только поля, шага фс нет

- UPD-03. Ленивое обновление индекса
  - Дано: пакет не объявлен, но файл может присутствовать на диске
  - Когда: выполняется обновление
  - Тогда: сначала выполняется ленивое обновление индекса — поиск файла на диске
  - Когда: файл найден
  - Тогда: заводится запись, обновление отрабатывает как обычно
  - Когда: файл не найден
  - Тогда: ошибка

- UPD-04. Полное совпадение параметров
  - Дано: все параметры совпадают, хэшсумма просчиталась аналогичной
  - Когда: выполняется обновление
  - Тогда: ошибка

- UPD-05. Сбой записи файла
  - Дано: шаг записи файла в фс не удался
  - Когда: выполняется обновление
  - Тогда: операция не фиксируется в бд (см. Атомарность)

*** Удаление пакета

- DEL-01. Удаление всего, что связано
  - Когда: удаляется пакет
  - Тогда: удаляется все, что связано с пакетом: все версии, записи в бд, файлы/ссылки в фс, журналы тест/сборки
  - Тогда: фантом (пакет без версий) удаляется целиком

*** Тестирование пакета

- TST-01. Фантом нельзя тестировать
  - Дано: пакет-фантом без версии
  - Когда: запрашивается тестирование
  - Тогда: ошибка — журнал тестирования привязан к версии

- TST-02. Запись о начале тестирования
  - Дано: пакет-версия, url для теста задан
  - Когда: вызывается функция тестирования
  - Тогда: в журнал пишется запись о начале тестирования

- TST-03. Статус по последней валидной записи
  - Дано: процесс завершился и передал результат через колбэк
  - Когда: вычисляется статус верификации
  - Тогда: статус считается по последней завершенной валидной записи, а не хранится

- TST-04. Недействительная запись игнорируется
  - Дано: последняя завершенная (успешная) запись помечена недействительной
  - Когда: вычисляется статус верификации
  - Тогда: недействительная запись игнорируется — она не влияет на статус

- TST-05. Сбой запуска процесса
  - Дано: оркестратор/процесс не смог запуститься
  - Когда: запрашивается тестирование
  - Тогда: ошибка записывается в журнал обычным образом

- TST-06. url теста не задан
  - Дано: для пакета не установлен url для запуска теста
  - Когда: запрашивается тестирование
  - Тогда: используется общий url, если он настроен
  - Дано: общий url также не настроен
  - Тогда: ошибка

- TST-07. Ответ запуска сохраняется в журнал
  - Дано: процесс запущен, url запуска содержит id через шаблонизатор
  - Когда: оркестратор возвращает ответ на вызов url запуска
  - Тогда: ответ сохраняется в запись журнала
  - Когда: запускается процесс с шаблонизированным url
  - Тогда: id подставляется в url запуска

*** Колбэк процессов

- CBK-01. Результат из переменных url колбэка
  - Дано: url колбэка содержит обязательные переменные шаблона (`{result}`), которые заполняет раннер
  - Когда: раннер вызывает колбэк
  - Тогда: сервер парсит `{result}` из url (`ok`/`fail`) и сохраняет в запись журнала
  - Тогда: body колбэка (plain text) сохраняется как есть, не обрабатывается

- CBK-02. Повторный колбэк
  - Дано: колбэк с этим id уже обработан
  - Когда: приходит повторный колбэк с тем же id
  - Тогда: запись не перезаписывается, колбэк игнорируется

- CBK-03. Колбэк с несуществующим id
  - Когда: колбэк приходит с id, которого нет в журнале
  - Тогда: колбэк игнорируется, в лог пишется предупреждение

*** Сборка пакета

- BLD-01. Сборка фантома через any
  - Дано: пакет-фантом без версии
  - Когда: запрашивается сборка
  - Тогда: сборка возможна с версией `any` (меткой отсутствия версии)

- BLD-02. Раннер обязан дать версию
  - Дано: сборка запущена с версией `any`
  - Когда: приходит результат от раннера
  - Тогда: раннер обязан предоставить конкретную версию
  - Когда: версия результата равна `any`
  - Тогда: ошибка

- BLD-03. Статус сборки по последней валидной
  - Дано: процесс завершился
  - Когда: вычисляется статус сборки
  - Тогда: статус считается по последней завершенной валидной записи; недействительные игнорируются

- BLD-04. Недействительность сборки
  - Когда: сборка помечается недействительной
  - Тогда: запись игнорируется при вычислении статуса

- BLD-05. Отдельные сущности сборки
  - Дано: url и журнал сборки — отдельные сущности (свои url, свой журнал), не переиспользуемые с тестированием

** Парсинг имени файла

- PRS-01. rpm: имя-версия-релиз
  - Дано: rpm-файл с именем по шаблону `имя-версия-релиз` (например `nginx-1.24.0-1.el9.rpm`)
  - Когда: имя файла разбирается по шаблону rpm
  - Тогда: имя = `nginx`, версия = `1.24.0`, релиз — часть версии (`1.24.0-1.el9`)

- PRS-02. rpm с версией-релизом без разделителей
  - Дано: rpm-файл без релиза (например `nginx-1.24.0.rpm`)
  - Когда: имя файла разбирается
  - Тогда: имя = `nginx`, версия = `1.24.0`

- PRS-03. deb: имя_версия_архитектура
  - Дано: deb-файл с именем по шаблону `имя_версия_архитектура` (например `nginx_1.24.0_amd64.deb`)
  - Когда: имя файла разбирается по шаблону deb
  - Тогда: имя = `nginx`, версия = `1.24.0`, архитектура отдельным полем не становится

- PRS-04. Неразбираемое имя
  - Дано: файл, не соответствующий шаблону (например `README.txt` или `nginx.rpm`)
  - Когда: выполняется разбор
  - Тогда: разбор невозможен — ошибка

- PRS-05. Имя файла из разобранных полей
  - Дано: имя и версия из PRS-01..03
  - Когда: имя файла собирается обратно по шаблону пакетной системы
  - Тогда: получается исходное имя файла

** Репозитории

- REP-01. Создание репозитория
  - Дано: директория проинициализирована как репозиторий (маркеры: rpm — `repodata/`, deb — `Packages`/`Release`)
  - Когда: создается репозиторий с именем, путём и типом (rpm/deb)
  - Тогда: репозиторий создается

- REP-02. Создание с несуществующей директорией
  - Когда: путь репозитория не существует
  - Тогда: ошибка

- REP-03. Создание с непроинициализированной директорией
  - Когда: директория существует, но не проинициализирована (нет маркеров типа)
  - Тогда: ошибка

- REP-04. Дубликат имени репозитория
  - Когда: репозиторий с таким именем уже существует
  - Тогда: ошибка

- REP-05. Список репозиториев
  - Когда: запрашивается список репозиториев
  - Тогда: возвращаются все репозитории

- REP-06. Получение репозитория
  - Когда: запрашивается репозиторий по имени
  - Тогда: возвращается его конфигурация
  - Дано: репозитория с таким именем нет
  - Тогда: ошибка

- REP-07. Удаление репозитория
  - Когда: удаляется репозиторий
  - Тогда: запись репозитория удаляется (файлы в директории не удаляются)
  - Дано: пакеты размещены в этом репозитории
  - Тогда: размещение обновляется — репозиторий исчезает из свойств пакетов

*** Перемещение между репозиториями

- MOV-01. Несуществующий репозиторий
  - Дано: размещение — операция обновления пакета с указанием репозиториев, которые должны его содержать
  - Когда: пакет размещается в репозитории, которого нет (не создан через /api/repos или удален)
  - Тогда: ошибка

- MOV-02. Пустой список репозиториев
  - Когда: новый список репозиториев устанавливается пустым
  - Тогда: ошибка

- MOV-03. Частичный сбой
  - Когда: произошел частичный сбой (в один репозиторий записалось, в другой нет)
  - Тогда: возвращается ошибка, применяется атомарность (см. Атомарность)

- MOV-04. Репозиторий — свойство пакета
  - Когда: пакет размещается в другом репозитории
  - Тогда: журналы тест/сборки и вычисляемые статусы не затрагиваются — репозиторий лишь свойство пакета
  - Тогда: файл пакета появляется в каждом репозитории из списка, ни один из них не является «оригиналом»

- MOV-05. Обновление бд репозитория
  - Когда: у пакета добавляется или перезаписывается файл
  - Тогда: для каждого репозитория пакета вызывается специфичная команда/скрипт обновления (репо-адаптер)

- MOV-06. Размещение обязательно при добавлении файла
  - Когда: пакету добавляется версия с файлом
  - Дано: пакет не размещен ни в одном репозитории
  - Тогда: ошибка — файлу негде жить

*** Найти пакет

- SRCH-01. Пустой запрос
  - Когда: задан пустой запрос (ни один фильтр не задан)
  - Тогда: возвращаются все пакеты

- SRCH-02. Комбинация фильтров
  - Когда: заданы несколько фильтров
  - Тогда: фильтры комбинируются, результат — пересечение условий

- SRCH-03. Фильтр по имени
  - Когда: фильтр по имени пакета (без версии)
  - Тогда: возвращаются все версии пакета одним плоским списком (агрегация в единый пакет не предусмотрена, группирует клиент)

- SRCH-04. Точные совпадения и шаблоны
  - Когда: совпадения по заданным значениям
  - Тогда: применяется точное совпадение, допускаются простейшие шаблоны `?` и `*` (или подобные)

- SRCH-05. Статус не определен
  - Дано: у пакета нет журналов процессов
  - Тогда: его статус не определен, фильтр по статусу его не задевает

- SRCH-06. Полная информация
  - Тогда: результат поиска возвращает полную информацию о найденных пакетах

** Работа с оркестраторами процессов

- ORCH-01. Нет процессов у пакета
  - Дано: у пакета не настроено ни одного процесса
  - Когда: вызывается тестирование или сборка
  - Тогда: ошибка — процесс для пакета не настроен

- ORCH-02. Параллельные запуски
  - Когда: запускаются несколько процессов одного пакета
  - Тогда: запуски могут выполняться параллельно (ответственность на оркестраторе/раннерах)

** Настройка сервера

- CFG-01. Валидация на старте
  - Когда: сервер запускается с некорректными настройками
  - Тогда: валидация на старте возвращает ошибку

- CFG-02. Приоритет источников
  - Когда: значение настройки задано в нескольких источниках
  - Тогда: приоритет (низший → высший): конфиг-файл, env, cli

- CFG-03. Настройки неизменны при запущенном сервере
  - Дано: сервер запущен
  - Когда: предпринимается попытка изменить настройки
  - Тогда: настройки не изменяются — это невозможно пока запущен сервер

** Аутентификация

- AUTH-01. Доступ без токена
  - Дано: в конфиге объявлены токены
  - Когда: запрос не содержит токен
  - Тогда: ошибка

- AUTH-02. Неверный токен
  - Дано: токены объявлены в конфиге
  - Когда: запрос содержит токен, отсутствующий в конфиге
  - Тогда: ошибка

- AUTH-03. Корректный токен
  - Дано: токены объявлены в конфиге
  - Когда: запрос содержит валидный токен
  - Тогда: запрос обрабатывается

- AUTH-04. Колбэк с токеном
  - Дано: запущен процесс, url колбэка содержит токен раннера
  - Когда: вызывается колбэк без токена
  - Тогда: ошибка
  - Когда: колбэк содержит токен
  - Тогда: колбэк принимается

** Атомарность

- ATOM-01. Компенсация при сбое записи в бд
  - Дано: шаг с фс удался (файл записан в репозиторий)
  - Когда: запись в бд не проходит
  - Тогда: записанное удаляется (компенсация), операция возвращает ошибку

- ATOM-02. Компенсация при частичном размещении
  - Дано: файл записан в несколько репозиториев
  - Когда: в один репозиторий записалось, в другой нет
  - Тогда: созданные ссылки/записи удаляются, операция возвращает ошибку
