* Описание тесткейсов в стиле BDD свободным текстом

* Сервер

- Бд не подключена.
  - Любой запрос, требующий обращения к БД, возвращает ошибку.

- Каждый запрос(команда) получает id
  - id короткий и уникальный
  - Каждая операция от инициализации до завершения передает id
  - Логи содержат id запроса
  - url запуска процесса поддерживает шаблонизатор, id передается через url
  - url колбэка также содержит id, оркестратор передает в него отчёт

    
** Работа с пакетами

- Обращение к несуществующему пакеты.
  - Ошибка.


*** Добавление пакета

- пакет существует той же версии
  - ошибка

- В бд нет пакета с таким именем и версией.
  - Функция добавления вызвана.
  - Пакет записывается в фс (или перезаписывается), бд репозитория обновляется специфичной для репозитория командой/скриптом.
  - Теперь в бд есть запись, статус соответствует тому что указан, тип репозитория с пакетной системой и остальное — так же соответствует.
  - атомарность — см. Атомарность

- добавление/обновление пакета может сопровождаться установкой url для запуска процессов пакета

- пакет может быть фантомным: объявлен через апи, файла в фс нет
  - например, еще не собранный пакет
  - запись в бд есть, на диске файла нет
  - версии у фантома нет — версия появляется только из файла-артефакта

- в имени файла пакета в фс уже содержатся имя и версия
  - пока — парсинг имени файла по шаблону пакетной системы: rpm `имя-версия-релиз`, deb `имя_версия_архитектура`
  - парсинг хрупок на нестандартных именах, при невозможности разбора — ошибка (позже можно подключать апи репозитория)

- имя пакета (без версии) — ключ, связывающий пакеты одного имени с разными версиями


*** Обновление пакета

- обновление несуществующего пакета
  - ошибка

- В репозитории есть пакет, ровно с теми же параметрами, но отличается хэшсумма.
  - Вызов функции.
  - В фс пакет перезаписался, бд репозитория обновлена (как при добавлении).
  - Варнинг.
  - хэшсумма относится к индексации в фс (учитывает вес файла и т.д.), после перезаписи пересчитана

- файл есть в фс, но в бд записи еще нет
  - не отдавать сразу ошибку, а выполнить ленивое обновление индекса: сначала найти файл и завести запись
  - после этого обновление отрабатывает как обычно

- cовпадение всех параметров, хэшсумма просчиталась аналогичной
  - ошибка

- атомарность обновления «файл + бд»
  - если не удалось обновить файл, операция не зафиксируется в бд
  - далее — см. Атомарность


*** Удаление пакета

- удаление пакета
  - удаляется все, что связано с пакетом: все версии, записи в бд, файлы/ссылки в фс, журналы тест/сборки
  - атомарность — см. Атомарность

     
*** Тестирование пакета

- журнал тестирования связан с версией пакета
  - фантомный пакет без версии не может участвовать в тестировании

- Вызов функции
  - пакет получил запись о начале тестирования

- пакет содержит журнал запусков тестирования
  - статус верификации — вычисляемое значение по последнему завершенному валидному тестированию, а не хранимое
  - недействительные записи игнорируются при вычислении, даже если это последняя завершенная (успешная)
  - за изменением журнала следует изменение статуса
  - статус всегда актуален и опирается на результаты процессов

- журнал хранит все записи
  - id записи журнала берется из id инициализирующего запроса и устанавливается из кода, а не генерируется бд/случайным механизмом
  - группировка записей журнала по id запроса

- колбэк принимает отчёт процесса
  - body — пока просто текст в свободной форме, никак не обрабатывается
  - тело может быть ссылкой на внешний отчёт — это тоже plain body, не обрабатываем сейчас
  - структурированный результат передается переменными шаблона url колбэка (например `{result}`)
    - обязательные переменные шаблона — часть контракта и документируются, заполняет их раннер
    - сервер парсит их из url и сохраняет, body сохраняет как есть
    - один колбэк, несколько не предусмотрены

- оркестратор/процесс не смог запуститься — ошибка
  - ошибка записывается в журнал обычным образом

- тестирование можно помечать недействительным
  - недействительные записи не влияют на вычисляемый статус, даже если запись последняя

- Для пакета не установлен url на запуск запрос теста
  - использовать общий url если настроен
  - url не настроен
    - ошибка

	
*** Сборка пакета

- привязка к версии сборке не обязательна
  - версия для сборки может быть `any` — любая, которую сможет достать раннер
  - фантом без версии не может участвовать в тестировании, но в сборке может — как раз через `any`
  - как раннер получает версию — вне зоны сервера, ответственность конкретного раннера (например гит-теги с префиксом имени программы)

- аналогично тестированию, за исключением переменных
  - свой журнал сборки
  - свои url
  - свой вычисляемый статус сборки по последней завершенной валидной, а не хранимое значение — недействительные игнорируются
  - тестирование и сборка похожи, но url и журналы в коде и бд — разные сущности, не переиспользуемые модели
    - полиморфная модель в бд потребовала бы jsonb, избегаем
    - разные модели — чтобы не делать преждевременную оптимизацию

- сборку можно помечать недействительной — применимо как к тестированию


*** Перемещение пакетов между репозиториями 

- слово «перемещение» — это выбор репозиториев, в которых пакет будет размещаться, физически создание ссылок (как `ln`), а не копирование

- пакеты связаны с репозиториями, то есть с директориями в файловой системе, уже проинициализированными как репозитории (rpm, deb и т.д.)
  - проверка проинициализированности — через репо-адаптер (та же команда/скрипт, что обновляет бд репозитория)
    - запасной вариант — маркеры формата: rpm — repodata/, deb — Packages/Release

- когда репозитория не существует
  - попытка разместить в нем пакет вернет ошибку

- размещение в репозиториях — это операция обновления пакета, с указанием репозиториев, которые должны его содержать

- вызов обновления с попыткой установить новый список как пустой
  - вернет ошибку

- частичный сбой (в один репозиторий записалось, в другой нет)
  - отображается как ошибка
  - см. Атомарность

- репозиторий — это лишь свойство пакета
  - размещение в другом репозитории не затрагивает журналы тест/сборки и вычисляемые статусы

 

*** Найти пакет

- поиск принимает
  - название пакета
  - версию
  - репозиторий
  - вычисленные статусы из журналов процессов

- пустой запрос (ни один фильтр не задан)
  - возвращаются все пакеты

- фильтры комбинируются между собой — результат это пересечение условий

- пагинация и сортировка не нужны

- совпадения пока точные, допускаются простейшие шаблоны `?` и `*` (или подобные)

- релиз — часть версии, отдельного поля/фильтра нет

- результат поиска возвращает полную информацию о найденных пакетах

- у пакетов без журналов процессов статус не определен
  - фильтр по статусу их не задевает

- фильтр по имени возвращает все версии пакета одним плоским списком
  - агрегация в единый пакет не предусмотрена, группирует клиент

** Работа с оркестраторами процессов

- процессы задаются в связке с пакетом, то есть по имени пакета, а не по конкретной версии

- пакет может и вовсе не включать никакие процессы
  - в таком случае вызовы протестировать или собрать пакет вернут ошибку
    - так как процесс для данного пакета не настроен

- запуски процессов могут выполняться параллельно
  - ответственность за сериализацию/параллелизм — на оркестраторе и раннерах

- таймауты процессов не предусмотрены

** Настройка сервера

- источник конфигурации: env, затем cli — cli может переписать значение из конфига
  - конфиг-файл указывается через cli или берется из пути по умолчанию
  - приоритет (низший → высший): конфиг-файл, env, cli

- придерживаться gnu стандартов по конфигурации, fhs и т.д. — во всем проекте

- настройки валидируются на старте
  - некорректные настройки — ошибка

- нельзя изменить настройки пока запущен сервер

* Атомарность операций (фс + бд)

- применимо к добавлению, обновлению, удалению и размещению в репозиториях

- порядок: сначала фс, и только потом бд
  - запись в фс не выполняется в рамках транзакции бд
    - транзакция бд не может откатить фс, а долгая фс-операция внутри транзакции держит блокировки и мешает другим операциям
    - паттерн: файл пишется во временный файл + атомарный rename, затем короткая транзакция бд

- если шаг с фс удался, а запись в бд не прошла — компенсация: удалить записанное
  - один репозиторий — удалить файл
  - несколько репозиториев — удалить созданные ссылки
