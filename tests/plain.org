* Требования (ТЗ)

** Модель данных

- имя — первичная группирующая сущность («группа пакетов»); извлекается из содержимого спека или пакета при разборе файла, клиентом не задается
- загрузка спеков и пакетов — раздельные методы/эндпоинты
- спек — файл со своей версией; у имени может быть несколько спеков
- пакет — артефакт: файл с версией и опциональной ссылкой на спек, которым собран; ссылка — история для группировки по спеку, функционально ни на что не влияет
- пакет без спека — норма (синк фс находит артефакты без истории сборки)
- фантомов нет: имя создается только первой загрузкой валидного спека или пакета; пустое имя через API не создать
- обратной совместимости со старой моделью нет, проект не запущен
- валидация загружаемого спека или пакета обязательна; невалидные данные — ошибка, имя не создается
- имя и версия берутся из файла при разборе: утилита пакетной системы (`rpm -qp`); использование утилит задается в конфиге, бинарники находятся через `env`/PATH
  - если использование утилит включено, но утилита не найдена или не выполнилась — варнинг и фолбэк на парсер имени файла
  - парсер имени файла по шаблону пакетной системы (`{name}-{version}-{release}.{arch}.rpm`) — фолбэк, когда утилита недоступна/не смогла разобрать; при невозможности разбора — ошибка (в API) / только лог (в синке)
- результат разбора — только имя и версия (минимум полей); релиз и архитектура входят в version-строку, отдельного поля/фильтра нет
- поддерживается только тип репозитория `rpm`; поддержка прочих пакетных систем вырезана
- соответствие версии пакета версии/ревизии внутри спека не проверяется — расхождение допустимо (логическая ошибка пользователя), система не отвергает
- дедуп выполняется до записи в фс:
  - спек — по хэшу содержимого (+ имя и версия спека)
  - пакет — по хэшсумме файла + имени + версии
  - дубль — ошибка; флаг override — перезапись записи и файла «втупую», пересчет хэша; существующие ссылки (пакетов на спек) не трогаются и не ломаются
- для синка фс дубль — пропуск (идемпотентность)
- переименование — это новое имя и удаление старого
- схема бд проектируется на этапе реализации
- веб-интерфейс: код фронта вырезан, зависимости не удаляются

** Сервер

- каждый запрос (команда) получает id: короткий и уникальный
- id пробрасывается через все слои от инициализации до завершения операции
- логи содержат id запроса
- логи — stdout, структурированные
  - цвета — только при выводе в терминал (TTY); в пайп/файл лог остается plain
  - ключи стандартных полей (time/level/logger/msg) скрыты по умолчанию, значения сохраняются; показ ключей — конфиг `LOG_STANDARD_FIELDS` (список через запятую)
- api — http, данные в json
# закомментировано вместе с процессами/журналами (см. ниже):
# - url запуска процесса поддерживает шаблонизатор, id передается через url
# - url колбэка также содержит id, в него оркестратор передает отчёт
- если БД недоступна — любой запрос, требующий обращения к БД, возвращает ошибку

** Аутентификация

- доступ по токенам; токены объявляются в конфиге: значение, комментарий (назначение), роль
- токены бессрочные, не истекают
# - url колбэков для раннеров содержат токен

** Репозитории

- размещение пакета в репозиториях — это выбор репозиториев, в которых пакет будет размещаться; физически это создание ссылок (как `ln`), а не копирование
  - `ln` создает жесткую ссылку: после этого один inode имеет несколько имен (директорий); понятия «оригинал» и «копия» не существует — ни одна из директорий не является «исходной»
  - отдельного хранилища оригиналов нет; файл пакета физически лежит в репозиториях (в один или несколько)
- репозиторий — лишь свойство артефакта; размещение не затрагивает ничего, кроме размещения
- репозитории — директории в файловой системе, проинициализированные как репозитории (rpm)
  - `REPO_ROOT` обязателен в конфиге (подготовленный корневой каталог, обязан существовать) — сервер умеет создавать и инициализировать пути сам: путь из запроса трактуется относительно корня (или абсолютным, но внутри корня), отсутствующие каталоги создаются, отсутствующие маркеры формата создаются сервером
  - пути вне `REPO_ROOT` (в т.ч. выход через `../`) — ошибка
- проверка проинициализированности — через репо-адаптер (та же команда/скрипт, что обновляет бд репозитория); запасной вариант — маркер формата (rpm — каталог `repodata/`)
- создание маркера при автоинициализации: rpm — каталог `repodata/`; индекс (repodata/repomd.xml) перестраивается при добавлении файлов (см. MOV-05)
- добавление/перезапись файла сопровождается обновлением бд репозитория специфичной для репозитория командой/скриптом
- хэшсумма относится к индексации в фс (учитывает вес файла и т.д.)

# ** Процессы и оркестраторы
#
# Раздел закомментирован до переосмысления журналов.
#
# - процессы задаются в связке с именем, а не по конкретной версии артефакта
# - запуски процессов могут выполняться параллельно; ответственность за сериализацию/параллелизм — на оркестраторе и раннерах
# - параллельные запуски разрешены и для одной версии пакета
# - таймауты процессов не предусмотрены

# ** Журналы и статусы
#
# Раздел закомментирован: журналы переосмысливаются, всё связанное с ними отложено.
#
# - журналы тестирования и сборки — разные сущности, не переиспользуемые модели
#   - полиморфная модель в бд потребовала бы jsonb, избегаем
# - журнал тестирования (и сборки) связан с версией пакета
# - журнал хранит все записи
# - id записи журнала берется из id инициализирующего запроса и устанавливается из кода, а не генерируется бд/случайным механизмом
# - группировка записей журнала по id запроса
# - статус верификации и статус сборки — вычисляемые значения по последнему завершенному валидному прогону, не хранимые
#   - недействительные записи игнорируются при вычислении, даже если это последняя завершенная (успешная)
# - тестирование и сборки можно помечать недействительными

# ** Колбэк процессов
#
# Раздел закомментирован вместе с журналами.
#
# - на запуск процесса один колбэк, несколько не предусмотрены
# - url колбэка содержит id запроса и токен раннера
# - body колбэка — plain text в свободной форме, никак не обрабатывается
# - структурированный результат передается переменными шаблона url колбэка (например `{result}`)
#   - обязательные переменные шаблона — часть контракта и документируются, заполняет их раннер
#   - сервер парсит их из url и сохраняет, body сохраняет как есть
# - `{result}` — фиксированный набор значений: `ok` / `fail`
# - ответ на вызов url запуска процесса сохраняется в запись журнала
# - колбэк с несуществующим id — игнорируется, предупреждение в лог
# - повторный колбэк — не перезаписывает запись, игнорируется

** Конфигурация

- источник конфигурации: конфиг-файл, env, затем cli
- приоритет (низший → высший): конфиг-файл, env, cli
- конфиг-файл указывается через cli или берется из пути по умолчанию
- придерживаться gnu стандартов по конфигурации, fhs и т.д. — во всем проекте
- `DATABASE_PATH` — путь к файлу бд, обязателен, значения по умолчанию нет
  - не задан ни в одном источнике (конфиг-файл, env, cli) — настройка некорректна, сервер не стартует (ошибка валидации на старте, см. CFG-01)
  - задан абсолютным — используется как есть; задан относительным — резолвится относительно рабочего каталога
- `REPO_ROOT` — корневой каталог репозиториев, обязателен, значения по умолчанию нет
  - не задан ни в одном источнике — настройка некорректна, сервер не стартует (см. CFG-05)
  - обязан существовать к моменту старта сервера (корень для авто-создания/инициализации путей)
  - задан абсолютным — используется как есть; задан относительным — резолвится относительно рабочего каталога
- настройки валидируются на старте, некорректные настройки — ошибка
- настройки (несекретные) печатаются в лог при старте
- настройки нельзя изменить пока запущен сервер

** Атомарность

- применимо к добавлению, обновлению, удалению и размещению в репозиториях
- порядок: сначала фс, и только потом бд
  - запись в фс не выполняется в рамках транзакции бд
    - транзакция бд не может откатить фс, а долгая фс-операция внутри транзакции держит блокировки и мешает другим операциям
    - паттерн: файл пишется во временный файл + атомарный rename, затем короткая транзакция бд
- дедуп-проверка выполняется до записи в фс (см. Модель данных)
- если шаг с фс удался, а запись в бд не прошла — компенсация: удалить записанное
  - один репозиторий — удалить файл
  - несколько репозиториев — удалить созданные ссылки

* Тесткейсы (BDD)

** Сервер

*** SVR-01. Запрос при недоступной БД

- Когда: поступает запрос, требующий обращения к БД, а БД недоступна
- Тогда: возвращается ошибка

*** SVR-02. id запроса

- Когда: сервер принимает запрос (команду)
- Тогда: запрос получает короткий уникальный id
- Тогда: id передается через все операции от инициализации до завершения
- Тогда: логи содержат id запроса
# закомментировано вместе с процессами/журналами:
# - Когда: запускается процесс
# - Тогда: id передается через шаблонизированный url запуска процесса
# - Когда: процесс завершается и вызывает колбэк
# - Тогда: url колбэка содержит id, в него передается отчёт процесса

*** SVR-03. Синхронизация с фс

- Когда: сервер периодически сканирует репозитории (или по ручному запросу)
- Тогда: подхватываются имена/артефакты, появившиеся на диске вне API
- Тогда: сканируются только файлы с расширением `.rpm`; файлы иных расширений игнорируются (индексные файлы rpm живут в каталоге `repodata/`)
- Тогда: разбор артефакта выполняется утилитой пакетной системы (если включено в конфиге) с фолбэком на парсер имени файла по шаблону (`{name}-{version}-{release}.{arch}.rpm`)
- Тогда: артефакт без истории сборки заводится без ссылки на спек
- Конфиг: период фонового скана `SYNC_INTERVAL_SECONDS` (0 — выключить); ручной запуск — `POST /api/packages/sync`
- Тогда: фоновый и ручной скан используют одну и ту же логику и не запускаются одновременно (если предыдущий скан ещё идёт — пропуск)
- Тогда: неразбираемое имя файла только логируется, ошибкой не становится
- Тогда: повторный скан идемпотентен — дубликаты пропускаются, новых записей не появляется

** Имена

*** NM-01. Создание имени загрузкой спека

- Дано: имени нет
- Когда: загружается валидный спек
- Тогда: имя создается (парсится из спека) и запись спека появляется в бд

*** NM-02. Создание имени загрузкой пакета

- Дано: имени нет
- Когда: загружается валидный пакет
- Тогда: имя создается (парсится из пакета) и запись артефакта появляется в бд
- Тогда: артефакт не имеет ссылки на спек

*** NM-03. Дедуп спека

- Дано: у имени уже есть спек с идентичным содержимым
- Когда: загружается тот же спек без override
- Тогда: ошибка
- Когда: загружается с флагом override
- Тогда: запись спека и файл перезаписываются «втупую», хэш пересчитывается
- Тогда: ссылки пакетов на этот спек не изменяются и не ломаются

*** NM-04. Дедуп пакета

- Дано: существует артефакт с тем же именем, версией и хэшсуммой файла
- Когда: загружается пакет без override
- Тогда: ошибка
- Когда: загружается с флагом override
- Тогда: файл перезаписывается в фс, хэш пересчитывается, запись обновляется
- Тогда: ссылки (размещение, привязки) не ломаются

*** NM-05. Невалидные данные

- Когда: загружается невалидный спек или неразбираемый пакет
- Тогда: ошибка, имя не создается

*** NM-06. Имя извлекается из файла

- Когда: загружается спек или пакет
- Тогда: имя определяется только разбором содержимого файла, поле имени в запросе отсутствует

*** NM-07. Версия пакета vs версия спека

- Дано: пакет ссылается на спек, чья версия/ревизия не соответствует версии пакета
- Тогда: загрузка допускается — расхождение не проверяется (логическая ответственность пользователя)

** Добавление к существующему имени

- ADD-01. Артефакт к существующему имени
  - Дано: имя существует
  - Когда: загружается пакет с новой версией
  - Тогда: появляется новая запись артефакта, файл пишется в фс, бд репозитория обновляется

- ADD-02. Спек к существующему имени
  - Дано: имя существует
  - Когда: загружается новый спек (другая версия или другое содержимое)
  - Тогда: появляется запись спека

- ADD-03. Чужое имя
  - Дано: загрузка адресована существующему имени X
  - Когда: разбор файла дает имя Y != X
  - Тогда: ошибка

** Обновление пакета

- UPD-01. Перезапись при разной хэшсумме
  - Дано: существует артефакт (имя + версия)
  - Когда: загружается пакет с той же именем/версией, но другой хэшсуммой
  - Тогда: файл в фс перезаписывается, бд репозитория обновляется, хэш пересчитывается

- UPD-02. Полное совпадение — дубль
  - Дано: все параметры совпадают, хэшсумма та же
  - Когда: выполняется загрузка без override
  - Тогда: ошибка (см. NM-04); с override — перезапись

- UPD-03. Ленивое обновление индекса
  - Дано: артефакт не объявлен, но файл присутствует на диске
  - Когда: обращение к несуществующей версии (обновление)
  - Тогда: сначала ленивое обновление индекса — поиск файла на диске
  - Когда: файл найден
  - Тогда: заводится запись, операция отрабатывает как обычно
  - Когда: файл не найден
  - Тогда: ошибка

- UPD-04. Сбой записи файла
  - Дано: шаг записи файла в фс не удался
  - Когда: выполняется обновление
  - Тогда: операция не фиксируется в бд (см. Атомарность)

** Удаление имени

- DEL-01. Удаление всего, что связано

  - Когда: удаляется имя
  - Тогда: удаляются все связанные данные: спеки, артефакты (все версии), записи в бд, файлы/ссылки в фс
# журналы закомментированы:
#   - Тогда: удаляются журналы тест/сборки всех версий

** Парсинг имени файла

- PRS-01. rpm через утилиту
  - Дано: rpm-файл (например `bash-5.2.37-2.x86_64.rpm`), в конфиге включено использование утилит
  - Когда: файл разбирается утилитой `rpm -qp`
  - Тогда: имя = `bash`, версия = `5.2.37-2.x86_64`
  - Тогда: релиз и архитектура входят в version-строку, отдельными полями не становятся

- PRS-02. rpm с релизом-ос
  - Дано: rpm-файл `nginx-1.24.0-1.el9.x86_64.rpm`
  - Когда: файл разбирается утилитой
  - Тогда: версия = `1.24.0-1.el9.x86_64` (релиз+ос и архитектура — часть версии)

- PRS-03. Утилита не найдена/не выполнилась — варнинг и фолбэк
  - Дано: использование утилит включено, но утилита `rpm` не найдена или не смогла выполниться
  - Когда: выполняется разбор
  - Тогда: в лог пишется варнинг
  - Тогда: имя и версия берутся из имени файла по шаблону пакетной системы (`{name}-{version}-{release}.{arch}.rpm`)

- PRS-04. Утилиты не включены или утилита не смогла разобрать файл
  - Дано: использование утилит выключено в конфиге (или утилита выполнилась, но файл — не пакет)
  - Когда: выполняется разбор
  - Тогда: используется парсер имени файла по шаблону
  - Когда: файл не соответствует шаблону (например `README.txt` или `nginx.rpm`)
  - Тогда: разбор невозможен — ошибка (в API) / только лог (в синке)

- PRS-05. Имя файла из имени и версии
  - Дано: имя и версия из PRS-01..03
  - Когда: имя файла собирается обратно по шаблону пакетной системы
  - Тогда: собирается исходное имя файла (`bash-5.2.37-2.x86_64.rpm`) — версия содержит все компоненты

- PRS-06. Загрузка файла через API
  - Дано: файл передается бинарным телом POST/PUT (рекомендуемый Content-Type: `application/octet-stream`; запрос распознается как бинарный при любом не-JSON content-type); репозитории объявлены в query (`repositories` через запятую)
  - Когда: файл разбирается той же цепочкой утилит по временному файлу
  - Тогда: имя и версия определяются только из метаданных файла; имя/версия пакета в запросе отсутствуют
  - Тогда: в запросе допустимо имя ФАЙЛА (`filename`) — нужно только фолбэк-парсеру имени файла; это не имя пакета
  - Когда: файл невозможно разобрать
  - Тогда: ошибка (в отличие от синка, где неразбираемое — только лог)
  - Когда: загружается пакет, а репозитории не указаны
  - Тогда: ошибка — файлу негде жить (см. MOV-06)
  - Тогда: ошибка — файлу негде жить (см. MOV-06)

- PRS-07. Версия файла не совпадает с перезаписываемой версией (PUT)
  - Когда: при обновлении конкретной версии фактическая версия из метаданных файла отличается от версии в пути
  - Тогда: ошибка (имя всегда берется из файла, подмены не предусмотрено)

** Репозитории

- REP-01. Создание репозитория
  - Дано: директория проинициализирована как репозиторий (маркер: rpm — каталог `repodata/`)
  - Когда: создается репозиторий с именем, путём и типом (`rpm`)
  - Тогда: репозиторий создается
  - Дано: тип, отличный от `rpm`
  - Тогда: ошибка — поддерживается только rpm

- REP-02. Создание с несуществующей директорией
  - Дано: путь (относительный или абсолютный) внутри `REPO_ROOT`, каталог не существует
  - Когда: создается репозиторий
  - Тогда: каталог создается, репозиторий проинициализируется (см. REP-08)
  - Дано: путь вне `REPO_ROOT` (абсолютный или через `../`)
  - Тогда: ошибка

- REP-03. Создание с непроинициализированной директорией
  - Дано: директория существует и внутри корня, но не проинициализирована (нет маркеров типа)
  - Когда: создается репозиторий
  - Тогда: маркеры формата создаются сервером, репозиторий создается

- REP-04. Дубликат имени репозитория
  - Когда: репозиторий с таким именем уже существует
  - Тогда: ошибка

- REP-05. Список репозиториев
  - Когда: запрашивается список репозиториев
  - Тогда: возвращаются все репозитории

- REP-06. Получение репозитория
  - Когда: запрашивается репозиторий по имени
  - Тогда: возвращается его конфигурация
  - Дано: репозитория с таким именем нет
  - Тогда: ошибка

- REP-07. Удаление репозитория
  - Когда: удаляется репозиторий
  - Тогда: запись репозитория удаляется (файлы в директории не удаляются)
  - Дано: пакеты размещены в этом репозитории
  - Тогда: размещение обновляется — репозиторий исчезает из свойств пакетов

- REP-08. Автоинициализация под `REPO_ROOT`
  - Дано: `REPO_ROOT` задан в конфиге и существует к старту сервера
  - Когда: создается репозиторий по относительному пути внутри корня (например `rpm/bla`, `staging/2026/08`)
  - Тогда: отсутствующие каталоги создаются, отсутствующие маркеры формата создаются
  - Тогда: в бд сохраняется абсолютный путь внутри корня
  - Когда: путь вне корня
  - Тогда: ошибка (репозиторий не создается)

*** Перемещение между репозиториями

- MOV-01. Несуществующий репозиторий
  - Дано: размещение — операция обновления артефакта с указанием репозиториев, которые должны его содержать
  - Когда: артефакт размещается в репозитории, которого нет (не создан через /api/repos или удален)
  - Тогда: ошибка

- MOV-02. Пустой список репозиториев
  - Когда: новый список репозиториев устанавливается пустым
  - Тогда: ошибка

- MOV-03. Частичный сбой
  - Когда: произошел частичный сбой (в один репозиторий записалось, в другой нет)

  - Тогда: файл пакета появляется в каждом репозитории из списка, ни один из них не является «оригиналом»

- MOV-05. Обновление бд репозитория
  - Когда: у артефакта добавляется или перезаписывается файл
  - Тогда: для каждого репозитория вызывается специфичная команда/скрипт обновления (репо-адаптер)

- MOV-06. Размещение обязательно при добавлении файла

  - Дано: не указан ни один репозиторий
  - Тогда: ошибка — файлу негде жить

** Настройка сервера

- CFG-01. Валидация на старте
  - Когда: сервер запускается с некорректными настройками
  - Тогда: валидация на старте возвращает ошибку

- CFG-02. Приоритет источников
  - Когда: значение настройки задано в нескольких источниках
  - Тогда: приоритет (низший → высший): конфиг-файл, env, cli

- CFG-03. Настройки неизменны при запущенном сервере
  - Дано: сервер запущен
  - Когда: предпринимается попытка изменить настройки
  - Тогда: настройки не изменяются — это невозможно пока запущен сервер

- CFG-04. DATABASE_PATH обязателен при старте
  - Когда: `DATABASE_PATH` не задан ни в одном источнике (конфиг-файл, env, cli)
  - Тогда: валидация на старте возвращает ошибку, сервер не запускается
  - Когда: `DATABASE_PATH` задан относительным путем
  - Тогда: путь резолвится относительно рабочего каталога
  - Когда: `DATABASE_PATH` задан абсолютным путем
  - Тогда: используется как есть

- CFG-05. REPO_ROOT обязателен при старте
  - Когда: `REPO_ROOT` не задан ни в одном источнике (конфиг-файл, env, cli)
  - Тогда: валидация на старте возвращает ошибку, сервер не запускается
  - Дано: `REPO_ROOT` задан в конфиге
  - Когда: каталог корня не существует к старту сервера
  - Тогда: сервер не запускается (ошибка)
  - Когда: `REPO_ROOT` задан относительным путем
  - Тогда: путь резолвится относительно рабочего каталога
  - Когда: `REPO_ROOT` задан абсолютным путем
  - Тогда: используется как есть

** Атомарность

- ATOM-01. Компенсация при сбое записи в бд
  - Дано: шаг с фс удался (файл записан в репозиторий)
  - Когда: запись в бд не проходит
  - Тогда: записанное удаляется (компенсация), операция возвращает ошибку

- ATOM-02. Компенсация при частичном размещении
  - Дано: файл записан в несколько репозиториев
  - Когда: в один репозиторий записалось, в другой нет
  - Тогда: созданные ссылки/записи удаляются, операция возвращает ошибку
